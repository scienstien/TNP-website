# Historical placement schema

Official CSV template format, ordered upload workflow, validation rules and import history are documented in [the import guide](../docs/IMPORT-TEMPLATES.md). The import history table was added by migration 0008; normal imports never delete omitted historical records.

`schema.ts` defines the approved PostgreSQL/Drizzle target for twenty years of
placement data across all departments at NIT Tiruchirappalli. `index.ts` exports
the shared typed `db` instance and underlying `postgresClient`; development
connections are reused across Next.js hot reloads.

## Delivery and migration status

The target schema is deployed by migration `0005_institute_wide_schema`, and the
application is ported to it (analytics, student editor, company directory, outreach
tracker). The process-calendar UI still uses browser local storage; the database
event tables are not connected to it.

- Migrations `0000` to `0004` are unchanged and describe the previous MME schema.
- `0006_drive_hr_role_domain` is additive: nullable `drives.hr_name`/`hr_email`/
  `hr_phone_number` (backfilled once from each company's legacy contact) and nullable
  `drive_roles.domain` with a trimmed non-blank check. Nothing is dropped.
- `0005` is data-preserving: it renames the legacy tables `students`, `companies`
  and `placement_offers` (and their indexes) to `legacy_students`,
  `legacy_companies` and `legacy_placement_offers`, keeping every row, and then
  creates the target tables. Nothing is dropped. The legacy tables are not part of
  `schema.ts`; `db/legacy-schema.ts` describes `legacy_students` for the MME roster
  import script only.
- Copying the legacy rows into the target model (including each company's
  `visit_date` as PPT drive events) is a reviewed data migration that has not been
  done. Registration status has no default, so each legacy student needs a confirmed
  registration value before import.
- The migration adds `SUPERADMIN` to `user_role`, `users.department_id` and
  `outreach_contacts.department_id`, and creates a placeholder `mme` department
  that existing users and outreach contacts are assigned to; see "Departments and
  access".
- `npm run db:seed:departments` loads fictional data into the target schema. The
  old `db:seed` and `db:seed:dashboard` scripts targeted the legacy model and were
  removed.

TypeScript properties use camelCase; SQL names below use snake_case. UUID
primary keys are generated by PostgreSQL. They are internal identifiers, not
fields the college must supply in historical spreadsheets. Imports resolve the
existing programme/cohort/enrollment using confirmed source fields and reuse its
ID rather than generating duplicate master records.

## Academic entities

| Table | Key and attributes | Relationships / uniqueness |
| --- | --- | --- |
| `departments` | UUID `department_id`; required `code`, `name` | Unique department code; one department has many programmes. |
| `degrees` | UUID `degree_id`; required `code`, `level` (`UG`/`PG`) | Unique degree code; one degree classifies many programmes. |
| `programmes` | UUID `programme_id`; `department_id`, `degree_id`; nullable `specialization` | One department and degree per programme. The department/degree/specialization combination is unique, including the no-specialization combination. PG specialization is a required business rule; see pending enforcement below. |
| `cohorts` | UUID `cohort_id`; `programme_id`; required `graduation_year` | Unique `(programme_id, graduation_year)`; graduating year is not a placement-cycle identifier. |
| `gender_types` | Text `code` PK; required `label` | Controlled reference values; no assumed source categories are seeded by the schema. |
| `reservation_categories` | Text `code` PK; required `label` | Controlled reference values; no fabricated category/default. |
| `students` | UUID `student_id`; required `name`; nullable `gender_code` FK | A person, independent of academic enrollment. One person may have multiple enrollments, for example UG followed by PG. |
| `enrollments` | UUID `enrollment_id`; required `student_id`, `roll_number`, `cohort_id`; nullable `admission_year`, `reservation_category_code` FK | Unique nine-digit integer roll, 100000000-999999999. One student and one cohort per enrollment. Reservation category records the category for that enrollment. |

Student names remain required, trimmed, and 1-100 characters. Student-input
validation retains Unicode letters/combining marks, spaces, apostrophes, periods
and hyphens, with at least one letter and no digits or unrelated symbols.
Graduation and provided admission years are four-digit years. Department, degree,
specialization and graduating year are obtained through the enrollment's cohort
and programme rather than duplicated on students.

Delayed graduation and changes to historical cohort membership are explicitly
nonblocking for this delivery; no academic-progression history model is included.
Roll numbers remain immutable through editing. Enforcement of that immutability
must be retained when the enrollment editor is implemented.

## Placement cycles and registration

| Table | Key and attributes | Relationships / constraints |
| --- | --- | --- |
| `placement_cycles` | UUID `cycle_id`; unique required `code`; nullable `starts_on`, `ends_on` | Dates are informational. Cycles may overlap and need not have known boundaries. |
| `cycle_cohorts` | Composite PK `(cycle_id, cohort_id)`; both are FKs | Resolves the many-to-many cycle/cohort association. |
| `student_cycles` | Composite PK `(cycle_id, enrollment_id)`; required `cohort_id`, `registration_status` | Required registration is `REGISTERED` or `UNREGISTERED`, with no default. Composite FKs require the enrollment's actual cohort and an existing cycle/cohort association. |

One cohort may participate in multiple cycles, and one cycle may include many
cohorts. A student's participation is identified explicitly by cycle and
enrollment. Neither calendar year nor offer/event dates infer the cycle.

`UNREGISTERED` includes students who opt out and students who are academically
ineligible. There is no separate eligibility field or eligibility-audit model.
The college supplies trusted, complete roster data; there is no
`roster_completeness` flag/table. Required registration values must still be
provided or established from the confirmed source. Missing historical
registration cannot silently default to either value: flag it for resolution
before import. The two-value enum does not represent unknown registration.

Placement status is derived per student-cycle:

| Registration | Offer for that enrollment and cycle | Derived status |
| --- | --- | --- |
| `REGISTERED` | Present | `PLACED` |
| `REGISTERED` | Absent | `UNPLACED` |
| `UNREGISTERED` | Absent | `UNREGISTERED` |
| `UNREGISTERED` | Present | Invalid cross-table state; see pending enforcement. |

For an agreed registered-student placement percentage, use placed enrollments
divided by registered enrollments in the same filtered cycle/cohort population,
times 100. A zero denominator is undefined, not 0%. Reports using any other
denominator must state it explicitly. Do not reuse the legacy all-recorded-students
formula without revisiting the newly included unregistered population. Analytics
integration and final metric presentation remain a separate task.

## Companies, repeated drives, roles and final offers

| Table | Key and attributes | Relationships / constraints |
| --- | --- | --- |
| `companies` | UUID `company_id`; unique required `name`; nullable `domain`, `hr_name`, `email`, `phone_number`, `pvr_status`, `remarks` | Stable identity across years and renames; company names no longer serve as offer FKs. `domain` is only a company description (never used for filtering or analytics). `hr_name`/`email`/`phone_number` are legacy global contacts, kept but no longer edited; drives carry their own HR contact. |
| `drives` | UUID `drive_id`; required `company_id`, `cycle_id`; nullable `reference`, `hr_name`, `hr_email`, `hr_phone_number` | Each drive belongs to one company and one cycle; repeated company/cycle combinations are allowed. The HR contact is required by the application on create/edit (0006 copied each company's legacy contact into its existing drives); the columns stay nullable for older rows. |
| `drive_roles` | UUID `role_id`; required `drive_id`; nullable `job_title`, `domain` | Repeated titles are allowed. The application requires at least one titled role when a drive is created and refuses to delete a drive's last role. `domain` is the role's field (Software, Production, …) and is what analytics use for distribution across fields. |
| `placement_offers` | UUID `offer_id`; required unique `enrollment_id`, required `cycle_id`, `company_id`; nullable `drive_id`, `role_id`, `package_lpa`, `monthly_stipend_inr`, `offer_type`, `offer_date` | Exactly one student-cycle and company per offer. Zero or one final reported offer per enrollment across all cycles. Optional drive/role references must match their company, cycle and parent drive. A role requires a drive. |

The same company may return many times in one cycle, with the same or different
role titles and different actual compensation for individual selected students.
No unique company/year/date/role/package combination limits those records.
Historical offers or PPOs can be recorded without inventing an unknown drive or
role. There are no role-target or advertised-package-variant tables in this model.

Compensation belongs to the individual final reported offer. `package_lpa` is
annual INR lakhs; `monthly_stipend_inr` is monthly INR, not LPA. Both are nullable
PostgreSQL numeric values, returned by Drizzle as strings to preserve precision.
Convert source values only when their currency, amount and period are reliable.
Missing amounts remain NULL. Offer type remains nullable `PPO`, `FTE` or
`FTE+6month`; it is not placement status. Offer date remains nullable.

The retained record is the final reported offer, rather than an offer lifecycle
ledger. Revocation clears the recorded offer. Multiple source offers for one roll
must be reported and resolved against the one-final-offer rule, never silently
dropped or accommodated by relaxing uniqueness. A student cannot retain an offer
while unregistered in its cycle.

PVR's exact business meaning remains unresolved. Preserve nullable yes/no/unknown
without inferring company/contact behavior. Company profile and per-cycle contact
history are outside this target model.

## Drive events and role selection

`drive_events` has UUID `event_id`, required `drive_id`, `process_type` and `scope`,
and nullable `scheduled_date` and `label`. Stages are `PPT`, `OT`, `GD`,
`RESUME_SHORTLISTING` and `PI`. Scope is `WHOLE_DRIVE` or `SELECTED_ROLES`.
Multiple events of the same stage may belong to one drive; an event may be undated.

`event_roles` resolves the event/role many-to-many relationship using composite
PK `(event_id, role_id)` and required `drive_id`. Composite FKs require the event
and role to belong to that same drive. A whole-drive event must have no selected
role links; a selected-role event must have at least one. This cardinality rule
needs enforcement beyond ordinary row checks/FKs.

The target has no `companies.visit_date`. Dated processes belong to drives/events,
so repeated visits do not overwrite one company-wide date. The old visit-date
migration stays intact; existing values need an explicit data-migration mapping.
Do not silently discard them or fabricate drive/cycle identities. The existing
local-storage calendar and dormant legacy calendar query/action files remain
unintegrated.

## Enforcement boundaries

`schema.ts` defines keys, uniqueness, local checks and composite FKs, including
enrollment/cohort consistency, offer company/cycle/drive/role consistency and
event/role same-drive consistency. It does not implement all cross-table rules.
The following need coordinated transactional write paths and, where appropriate,
database triggers before production integration:

- Require a specialization when the referenced degree is PG.
- Prevent offers for unregistered participation, including later registration
  changes that would invalidate an existing offer.
- Enforce zero role links for `WHOLE_DRIVE` events and at least one for
  `SELECTED_ROLES`, including scope edits and deletion of a last role link.
- Preserve roll-number immutability through the new enrollment editor.

Do not claim these rules are enforced merely because the target tables exist.
Likewise, schema changes do not provide authorization: protected reads/writes
must still use the authenticated database role on the server.

## Departments and access

`users` is exclusively for authentication/authorization: UUID `id`, nullable
`name`, unique required `email`, nullable `password_hash`, required `role`
(`ADMIN`, `PROFESSOR` or `SUPERADMIN`, default `PROFESSOR`) and a nullable
`department_id` FK to `departments`. `SUPERADMIN` has no department; the other
roles must have one (enforced by the application, not a constraint). It is not an
enrollment/student table or an Auth.js adapter schema. Auth.js Credentials/JWT
authentication is implemented; see `lib/auth/README.md`.

Department scoping is enforced on the server by `resolveDepartment()` in
`lib/auth/dal.ts`: PROFESSOR users are pinned to their own department; ADMIN and
SUPERADMIN users select a department using a cookie re-checked against the database,
or read all departments. Writes requiring a department are unavailable in the
all-departments view. Placement tables have no department
column: a department is reached through programme, cohort and enrollment.
The top Programme selector changes the UG/PG route for Dashboard and Student
Records and retains that navigation preference in browser storage; it does not
change a user's department or the database. The route level is rechecked on
student reads and writes.
Professors remain read-only; administrators (and the super admin) perform authorized
writes through `requireRole('ADMIN')`, which admits `SUPERADMIN`.

`outreach_contacts` is an independent contact/to-do list, without placement FKs or
synchronization, but each row belongs to one department (`department_id`, required).
Its company-name text, optional contacts/remarks, PVR default false and
server-maintained `updated_at` are otherwise unchanged. Signed-in professors may
read their department's list; only administrators may create, edit or delete its
entries.

Migration 0005 creates an `mme` department so existing accounts and contacts stay
valid. `npm run db:seed:departments` keeps it as the real Metallurgical and Materials
Engineering department: the full demo seed covers the nine B.Tech departments (chem,
civil, cse, ece, eee, ice, mech, mme, prod) and all 17 PG branches and their
specializations in `lib/placements/pg-catalog.ts`. Fictional PG programmes use the
published degree labels (M.Tech, M.Arch, M.Plan, M.Sc, MCA, MA and MBA).
The full seed creates exactly 10,000 fictional students and one enrollment and
student-cycle registration per student across graduating years 2008-2027. Both
degree levels appear in every year. Year totals grow gradually from 430 to 570;
department cohort sizes follow the demo department-size weights, each catalogue
specialization has a cohort in every year, and all final offers
belong to registered participation. These are synthetic distributions, not institute
statistics. The reset keeps user accounts and existing outreach contacts, and may add
missing fictional outreach contacts. `TARGET_STUDENTS=<positive integer>` optionally
overrides the full seed's student count for a smaller or larger disposable test dataset;
without it, the documented 10,000-student year distribution applies.
Shared demo definitions live in `db/demo-data.ts`. On a database the full seed refuses
(for example one holding legacy rows), the add-only
`DEMO_TOPUP_DATABASE=<name> npx tsx db/seed-departments-topup.ts` adds just the
departments that are missing or have no programmes, joining existing cycles and DEMO
company drives; it never deletes or updates rows and never touches `legacy_*` tables.

Migration 0007 adds the eight PG-only departments missing from the original nine-department
demo (Computer Applications, Energy and Environment, Physics, Architecture and
Planning, Chemistry, Mathematics, Humanities and Social Sciences, and Management
Studies). It preserves existing rows with a matching code or name and creates no
programmes or placement records. The top department selector reads these persisted
rows; `lib/placements/pg-catalog.ts` supplies published programme labels, which the
full disposable demo seed now uses for fictional PG records.
Real PG figures require matching degree, programme, cohort and registration rows.

## Local database and future migration workflow

The development scripts are `db:up`, `db:down`, `db:logs`, `db:migrate`, `db:check`,
`db:generate`, `db:studio` and `db:seed:departments`. Keep an untracked `.env` based on `.env.example`; both
Docker Compose and database scripts use the configured `DATABASE_URL`. Never
commit credentials or real student records.

`npm run db:up` starts the local PostgreSQL 17 container. `docker compose ps`
checks its status. It binds to `127.0.0.1` and persists data in the
`tnp_postgres_data` volume. `npm run db:down` stops it without removing data.
Do not remove the volume or reset an existing database for this schema change.

Before importing real data into the target:

1. Inspect actual historical source files and the preserved `legacy_*` tables;
   confirm programme/cohort mappings, registration and globally unique roll
   identities.
2. Plan the data migration preserving legacy data, keys and visit-date values.
   Keep migrations 0000-0005 unchanged. Do not accept generated destructive SQL
   without a reviewed data-preservation strategy.
3. Implement the cross-table transactional rules listed above and the calendar
   persistence in `drive_events`. Preserve server-side auth.
4. Reconcile imported counts and amounts against the legacy tables before retiring
   them.

`drizzle-kit generate` cannot create migration 0005 non-interactively because the
target reuses legacy table names; it was assembled by hand (table renames, then the
generated CREATE statements) and its snapshot matches `schema.ts`
(`npm run db:check` and `db:generate` report no drift). Use committed migrations
rather than `drizzle-kit push`. Neither migrations nor seeds are executed
automatically. No historical source files were inspected as part of defining this
target; actual mappings and missing values remain import work.

## Companies panel aggregate contract (2026-10-24)

Company-cycle directory membership requires a retained drive; All cycles lists all
company masters. Offer-only history remains valid without inventing a drive. No
new schema or migration is required by the panel integration.

Protected Companies reads aggregate final offers for matching REGISTERED
student-cycle rows through enrollment/cohort/programme department scope, including
UG and PG. Invalid offer/registration combinations produce a source-data error.
Drive/role metadata stay institute-wide, preserving repeated IDs and zero-offer
roles. Counts use Drizzle count() or explicit numeric decoding and are independently
reconciled against donut buckets.

Actual role compensation uses SQL aggregates: known amount count, median, minimum,
maximum. NULL is excluded, actual zero retained; LPA and monthly INR are never
combined. Only aggregates and role metadata leave the server. These read checks do
not replace the pending database enforcement work.
