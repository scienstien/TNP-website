## Summary of behavior change

| Situation | Before | After |
| --- | --- | --- |
| Deciding whether the data is "demo" | Roll < 900000000 or a company without the `DEMO ` prefix → refuse; anything else was treated as demo and deleted | **Never inferred from rolls or names.** The operator must set `DEMO_SEED_RESET_DATABASE` to the exact `current_database()` |
| Variable missing, blank, or naming another database | (not applicable) | Refused before any write |
| `NODE_ENV=production` | Ran | Refused |
| Any row in `legacy_students`, `legacy_companies`, `legacy_placement_offers` | Ignored | Refused, even when confirmed: the database is historical, not disposable |
| A target or legacy table cannot be counted | (not applicable) | Refused ("unknown dataset") |
| Confirmed database, target tables empty | Deleted (no-op) and inserted | `fresh`: insert only, no delete statements |
| Confirmed database, target tables non-empty | Deleted every target placement/academic row, then inserted | `reset`: same delete list (`DEMO_RESET_TABLES`), then insert |
| Existing department `civil`/`cse`/`ece`/`mech` with another name | Renamed to the demo name (`onConflictDoUpdate`) | Kept (`onConflictDoNothing`) |
| Retired `mme` department | Deleted all its outreach rows, deleted user `admin123mme@nitt.edu`, **moved every other user to `civil`**, deleted the department | Deleted **only** when no user, outreach record or programme refers to it; otherwise kept and logged. Users are never deleted, created or moved |
| Outreach contacts | Deleted rows matching `DEMO % (outreach)`, then inserted | Never deleted; a re-run only inserts the demo names a department does not have yet |

The fictional dataset itself (departments, programmes, cohorts, cycles, companies, drives,
roles, events, enrollments, registrations, offers) is generated exactly as before (same
PRNG seed 2027).

## File-by-file change log

### `db/seed-safety.ts` (added; pure, no imports)
- `DEMO_RESET_TABLES`: the 13 target tables the seed may empty, children first. This is
  the same list the seed previously deleted inline.
- `LEGACY_TABLES`: `legacy_students`, `legacy_companies`, `legacy_placement_offers`.
- `RESET_DATABASE_ENV = "DEMO_SEED_RESET_DATABASE"`.
- `interface SeedSnapshot { database: string; rows: Record<string, number> }`
- `interface SeedEnvironment { resetDatabase?: string; nodeEnv?: string }`
- `type SeedPlan = { mode: "fresh" | "reset" } | { refuse: string }`
- `planDemoSeed(snapshot, environment): SeedPlan`. Checks run in this order: production,
  confirmation present, confirmation matches, every table counted, no legacy rows, then
  `fresh` or `reset`.
- `canRemoveRetiredDepartment({ users, outreachContacts, programmes }): boolean`
- Why: TASKS.md MIG-003 asks for "an enforceable isolation check; refuse mixed/unknown
  datasets … never infer fictional ownership solely from names/rolls".

### `db/seed-safety.test.ts` (added)
Eight tests:
1. Refusal without, with a blank, or with a mismatched confirmation, for each TASKS.md
   fixture: 9-prefixed non-demo enrollment, standalone person, company-free data, empty.
2. A 9-prefixed roll is not provenance.
3. Production is refused.
4. Each legacy table with rows is refused.
5. An uncounted or negative count is refused.
6. A confirmed empty database gives `fresh`; a confirmed non-empty one gives `reset`.
7. The retired-department rule.
8. Two source checks on the seed: no `users` import or users write exists, and
   `planDemoSeed(` appears before the first write in `seed()`.

### `db/seed-departments-demo.ts` (modified)
- Header comment describes the new contract and run command.
- Imports:
  - removed `node:assert`, `and`, `like`, `not`, `notLike`, and the `users` table;
  - added the `./seed-safety` exports.
- Added `readSnapshot(tx)`:
  - reads `current_database()`;
  - checks `to_regclass()` for every counted table, with a missing legacy table counted
    as 0 and a missing target table left uncounted (so it is refused);
  - takes `count(*)` for each table.

  It is read-only and runs inside the seed's transaction.
- `seed()`:
  - the first statements are `planDemoSeed(...)`; a refusal throws, so the transaction
    rolls back with nothing written;
  - deletes run only in `reset` mode, over `DEMO_RESET_TABLES`.
- Department insert: `onConflictDoUpdate` is replaced by `onConflictDoNothing`.
- Retired-department block: replaced by a reference count plus
  `canRemoveRetiredDepartment()`.
- Outreach block: the pattern delete is removed; only missing demo names are inserted.
- Final log line names the mode and the database.

## Decisions and assumptions

- **Any legacy row means refuse.** A database holding the preserved MME history is not
  disposable, even if the operator confirms it. Developers whose local database went
  through migration 0005 with MME data must seed a **separate** database:

  ```bash
  # inside the PostgreSQL container or with psql against the same server
  createdb -U tnp_user tnp_demo
  # PowerShell: $env:DATABASE_URL="postgresql://tnp_user:<password>@localhost:5432/tnp_demo"
  DATABASE_URL=postgresql://tnp_user:<password>@localhost:5432/tnp_demo npm run db:migrate
  DATABASE_URL=postgresql://tnp_user:<password>@localhost:5432/tnp_demo DEMO_SEED_RESET_DATABASE=tnp_demo npm run db:seed:departments
  ```

  (`dotenv` does not override variables that are already set, so these values win over
  `.env`.) **Needs owner confirmation** if you would rather allow seeding next to legacy
  rows.
- **Confirmation is required even for an empty database.** The seed adds reference codes
  (gender, category, degrees), departments and outreach rows, which should not appear
  unasked in a real database.
- Gender, category and degree reference rows still use `onConflictDoNothing`; existing
  codes are never changed.
