## Scope statement

Student editor only: `lib/students/**`, `components/students/**`. The route
`app/(portal)/students/page.tsx` needed no change. This adds:
- stable student, enrollment, programme and cohort IDs;
- explicit participation keyed by (enrollment, cycle);
- explicit registration editing;
- a manual, nullable admission year;
- company options with IDs.

Out of scope:
- drive and role selection (MIG-005);
- optional stipend, gender and category fields (MIG-013, paused);
- cohort moves (still rejected);
- placement-cycle creation (decision D2: none in this round).

## Contract choice recorded at the checkpoint

TASKS.md allows "nested participations or a selected participation view". **Chosen:
nested participations.** Each `StudentRecord` is one enrollment, with a
`participations: StudentParticipation[]` array and a single `offer` carrying its own
`cycleId`. That mirrors the schema (one final offer per enrollment across cycles). The only
consumer is `components/students/StudentRecords.tsx` (Lane A). No other module imports
`lib/students/types.ts`; checked with `git grep -n "lib/students/types"`.

## Summary of behavior change

| Area | Before | After |
| --- | --- | --- |
| Programme on create | `ensureCohort()` took the department's first UG programme by UUID order | The admin chooses one of the department's UG programmes; the server checks department and level |
| Cycle on create | `ensureCycleId(batchYear)` derived the code "YYYY-1-YY" and **created** the cycle | No cycle is derived or created. Registration is optional: an existing cycle plus a chosen status |
| Registration on create | Always REGISTERED | Explicit REGISTERED or UNREGISTERED, or none at all |
| `admission_year` | `batchYear - 4` (fabricated) | Manual, nullable, four-digit, editable. Never derived |
| Registrations of an existing student | Not editable | Add, change status or remove per cycle. The cycle holding the offer cannot become UNREGISTERED or be removed |
| Cohort/cycle association | Created implicitly by `ensureCohort` | Created only when the admin explicitly registers a student for a cycle the cohort is not linked to; the UI says so before saving |
| Company on an offer | Matched by name | Chosen by `companyId` |
| Offer cycle | (MIG-001) offer's cycle, explicit, or single participation | Same; the editor shows the offer's cycle, or asks for one when there are several REGISTERED participations |
| Stale-edit snapshot | Roll, name, batch, offer fields | The full record, including all IDs, participations, statuses and offer ID |
| Duplicate-key errors | Every `23505` reported as "roll number exists" | Only `roll_number` constraints; others report a concurrent change |
| Roster status | Offer → Placed, otherwise Unplaced | Offer → Placed; REGISTERED without an offer → Unplaced; no REGISTERED participation → Not registered (AGENTS.md derivation) |
| Visit-date hint in the editor | `min` date from a cycle derived from today's date | Removed (it inferred the current cycle); the server check in the offer's cycle remains until MIG-005 |

### `lib/students/store.ts` (rewritten on top of MIG-001)
- Operations: `create | patch | removeOffer | removeStudent | setParticipation | removeParticipation`.
- `ensureCohort()` (first UG programme plus derived and created cycle) is replaced by

- `writeOffer()` resolves the company by `companyId`.
- `removeOffer` deletes by `offer_id`.
- A patch with a different `programmeId` or `batchYear` throws (cohort move rejected).
  `admissionYear` is updated when changed.
- The `lib/placements/cycles` import (`ensureCycleId`) is removed. `visitDatesByCompany`
  is still consumed unchanged.

## Decisions and assumptions (owner review requested where marked)

1. **Cohort/cycle association on explicit registration (needs owner confirmation).**
   Registering a student for a cycle the cohort is not yet linked to inserts the
   `cycle_cohorts` row. The schema requires that row, and the admin chose the cycle
   explicitly; the UI states it before saving. If associations must come only from
   source rosters, change `registerParticipation()` to reject instead.
2. **No placement-cycle creation (decision D2).** With no cycles in the database,
   registrations and offers cannot be recorded from the editor. Students can still be
   created without registration.
3. **Admission year has no ordering check** against the graduation year. No such rule is
   in AGENTS.md; only the four-digit check is enforced.
4. **New offer with exactly one REGISTERED participation:** the editor preselects that
   cycle visibly. The server also accepts it without `cycleId` when it is the only
   participation (MIG-001).
5. **Person reuse is not implemented.** Creating always creates a new person. Reuse
   needs an explicit identity and a shared-person policy, never a name match.
