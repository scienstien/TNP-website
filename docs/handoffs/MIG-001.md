## Scope statement

Lane A owns `lib/students/**`, `components/students/**`, `app/(portal)/students/**`,
`db/seed-departments-demo.ts` and `db/seed-safety*.ts`. This task changes only the student
write path: ambiguous or destructive participation and offer writes, the registration
requirement for offers, enrollment-only operations, and edits to a person shared across
departments. Explicit programme, cycle and registration editing is MIG-004. Drive and role
selection by ID is MIG-005. Neither is done here.

## Summary of behavior change

| Situation | Before | After |
| --- | --- | --- |
| Patch changes `batchYear` | `moveBatch()` deleted every `student_cycles` row and deleted then re-inserted the offer (new `offer_id`, drive/role dropped) in a cycle inferred from the year | Rejected with a `batchYear` field error; nothing is written |
| Offer write, enrollment has an offer | Updated by `enrollment_id`; date check and new role link used the first participation (`.limit(1)`), possibly another cycle | Uses the **offer's own cycle**; updated by `offer_id`; a request naming another cycle is rejected |
| New offer, 2+ participations | First participation (`.limit(1)`) chosen silently | Rejected unless `offer.cycleId` names one of them |
| New offer, exactly 1 participation | That participation | Unchanged |
| Offer write for UNREGISTERED participation | Allowed (the schema FK checks existence, not status) | Rejected ("An UNREGISTERED student cannot have an offer…") |
| Offer write and concurrent registration edit | Not serialized | The enrollment's `student_cycles` rows and its offer are locked `FOR UPDATE` before the decision |
| Rename, delete or remove an offer for an enrollment with **zero** participations | Failed with "no placement-cycle registration to edit" | Works; these operations no longer read participation |
| Rename a person who also has an enrollment in **another department** | The shared `students.name` was changed after locking only this enrollment | Rejected with a `name` field error; the `students` row is locked `FOR UPDATE` before the check |
| Rename when the only other enrollments are in the same department | Allowed | Allowed |
| Any rejection after a write inside the transaction | Some paths returned (committing earlier writes) | Every rejection after the first write **throws**, so the whole transaction rolls back |

## File-by-file change log

### `lib/students/rules.ts` (added)
- Exports:
  - `type RegistrationStatus = "REGISTERED" | "UNREGISTERED"`
  - `interface Participation { cycleId: string; registrationStatus: RegistrationStatus }`
  - `type OfferTarget = { cycleId: string } | { problem: string }`
  - `offerTarget(participations, offerCycleId: string | null, requestedCycleId?: string): OfferTarget`
  - `sharedPersonProblem(departmentId: string, otherEnrollmentDepartmentIds: readonly string[]): string | null`
- Pure (no `server-only`, no database), so it is unit-tested directly.
- Why: TASKS.md MIG-001 requires rejecting ambiguous participation and offer writes, requiring
  REGISTERED for offers, and detecting shared-person edits.

### `lib/students/rules.test.ts` (added)
- Six tests:
  - an existing offer stays in its own cycle with two participations;
  - a new offer with two participations needs an explicit cycle;
  - a single participation is the target;
  - zero participations are rejected;
  - UNREGISTERED is rejected for both new and existing offers;
  - shared-person department rule.

### `lib/students/store.ts` (modified)
- Removed: `moveBatch()` (internal, not exported). It was the destructive batch move.
- Removed: the `.limit(1)` participation lookup and its "no placement-cycle registration"
  error from the patch, removeOffer and removeStudent paths.
- `upsertOffer()` is renamed to the internal `writeOffer(tx, enrollmentId, patch)`:
  - locks the enrollment's `student_cycles` rows `FOR UPDATE`;
  - locks its offer `FOR UPDATE OF placement_offers`;
  - picks the cycle with `offerTarget()`;
  - updates `WHERE offer_id = …` instead of `WHERE enrollment_id = …`;
  - inserts new offers with the chosen cycle.

  The monthly stipend is still never written by the editor, so existing values are preserved.
- `linkRole()` now receives the offer's own student-cycle context, so a new role link is
  created in the offer's cycle and not in an arbitrary participation's cycle. The
  first-drive, first-title lookup itself is unchanged; it is MIG-005.
- Patch with a different `batchYear` throws a `batchYear` field error.
- Name change:
  - skipped when unchanged;
  - otherwise locks the `students` row and reads the departments of the person's other
    enrollments;
  - rejects through `sharedPersonProblem()` before writing.
- `mutateStudent` export signature is unchanged:
  `(departmentId, operation, input, roll?, expected?) => Promise<StudentResult>`.
- Lock order in every path: `enrollments` → `students` → `student_cycles` →
  `placement_offers`. One order prevents lock-order deadlocks.
- Create still infers the cohort and cycle from the batch year and registers the student
  as REGISTERED. TASKS.md assigns its replacement to MIG-004; it is unchanged here.

### `lib/students/types.ts` (modified)
- Added `export type OfferChanges = Partial<StudentOffer> & { cycleId?: string }`.
- `StudentChanges.offer` is now `OfferChanges` (it was `Partial<StudentOffer>`).
  `StudentRecord`, `StudentOffer` and `StudentData` are unchanged.

### `lib/students/validation.ts` (modified)
- The offer payload accepts an optional `cycleId`. It must be a UUID string and is
  normalized to lowercase. Anything else is an `offer` field error.

### `lib/students/validation.test.ts` (modified)
- Added: "an offer may name its placement cycle by UUID only".

### `components/students/StudentRecords.tsx` (modified)
- The "Graduating batch" input is read-only when editing an existing student, so the
  editor no longer offers a move the server rejects. Create is unchanged.

## Decisions and assumptions

- An existing offer is never moved to another cycle. Moving offers between cycles is not
  requested anywhere.
- Exactly one participation is treated as an unambiguous target, not inference: cycle
  membership is still explicit in `student_cycles`.
- Renames are allowed when all of the person's other enrollments are in the caller's
  department. They are rejected otherwise, pending an explicit ownership policy
  (TASKS.md MIG-001: "reject unsafe cross-department changes pending an explicit
  ownership policy").
- `removeStudent` still deletes the enrollment's participations before the enrollment. It
  is an explicit, confirmed deletion of that enrollment and is refused while an offer
  exists.
